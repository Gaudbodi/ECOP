<objective>
Fix the bug where the alert Termination modal closes abruptly mid-flow, before the
user confirms or cancels.

Purpose: A validator/admin typing a resolution reason loses the dialog (and their
typed reason) whenever unrelated alert traffic arrives over Socket.IO. This makes
terminating an alert unreliable and can drop a half-typed CAP Cancel reason.

Output: The Terminate (and Extend) dialogs stay open until the user explicitly
cancels, presses Esc, or submits — regardless of background alert updates.
</objective>

<root_cause>
DIAGNOSED ROOT CAUSE (file:line evidence):

The lifecycle dialogs are mounted inside the per-alert card subtree, and their
open/closed state is LOCAL to that subtree. A background list re-render that
reorders or remounts the card tears down that state mid-flow, which the native
`<dialog>` effect then interprets as a close request.

Chain:
1. `LifecycleControls` holds `terminateOpen` in local state (LifecycleControls.tsx:27)
   and renders `<TerminateDialog open={terminateOpen} .../>` (LifecycleControls.tsx:127-133).
   This component is mounted only inside the expanded card detail
   (AlertDetail.tsx:89 → AlertCard.tsx:54).
2. `Pipeline` renders one `AlertCard` per alert, keyed by identifier
   (Pipeline.tsx:104-106). `AlertCard` wraps everything in `motion.div layout` +
   `AnimatePresence` (AlertCard.tsx:29,44).
3. `useAlerts.onNew` prepends-and-reorders on EVERY `new_alert`:
   `setAlerts(prev => [a, ...prev.filter(x => x.identifier !== a.identifier)])`
   (useAlerts.ts:70). For an already-present identifier this MOVES the card to the
   top AND swaps its object reference. `onUpdated` also swaps the object reference
   (useAlerts.ts:73). The server emits these liberally — `new_alert` at
   ghana_cap_app.py:907 and `alert_updated` at ghana_cap_app.py:442 and
   ghana_cap_app.py:472 (`_broadcast_alert_update`, used by terminate + extend).
4. The reorder + `motion layout` reconciliation remounts the moved card subtree,
   unmounting `LifecycleControls`. Its `terminateOpen` resets to `false`. On remount
   the dialog effect sees `open === false` and calls `ref.current.close()`
   (LifecycleDialogs.tsx:29-37). The modal vanishes although the user never confirmed.

So unrelated background alert traffic — not the user — closes the dialog.

FIX STRATEGY (minimal, two layers of defense):
- Stop the gratuitous reorder/remount: in `onNew`, when the incoming identifier
  already exists, patch it IN PLACE (preserve array position and only swap that one
  entry) instead of `[a, ...rest]`. This removes the reorder that triggers the
  remount for the common same-identifier re-emission. (`onUpdated` already maps in
  place; keep it.)
- Defend the dialog against any remaining transient unmount: have the native
  `<dialog>` only close on EXPLICIT user intent (Cancel button → onCancel,
  native cancel/Esc → onCancel) or successful submit. A parent-driven `open`
  flip to false from a remount must not be the sole trigger that loses the
  in-progress reason. Concretely, the dialog keeps its own typed `reason` and the
  close path runs through `onCancel`/`onSubmit` only.
</root_cause>
