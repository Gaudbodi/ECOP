# Phase quick-260605-e7h Plan 01: Fix Alert Termination Modal Closing Abruptly Summary

In-place Socket.IO list reconciliation for already-present alerts plus edge-gated dialog state resets, so the Terminate/Extend modals survive background `new_alert`/`alert_updated` traffic and close only on explicit Cancel/Esc/submit.

## What Was Built

Two layers of defense against the bug where the alert Termination (and Extension) modal closed abruptly mid-flow when unrelated alert traffic arrived over Socket.IO:

1. **Primary fix — stop the reorder/remount (`useAlerts.ts`):** `onNew` previously did `[a, ...prev.filter(...)]`, which for an already-present identifier moved its card to the top of the list and swapped its object reference. The `motion.div layout` reconciliation in `AlertCard` turned that reorder into a subtree remount, which unmounted `LifecycleControls`, reset its local `terminateOpen` to `false`, and the dialog effect then called `ref.current.close()`. Now `onNew` patches an already-present identifier **in place** (same array index, `map` swap of only that element) and prepends **only** genuinely-new identifiers. `addAlert` was updated to mirror the same rule. `onUpdated` was already in-place and left unchanged. The dedup-by-identifier guarantee is preserved.

2. **Defense-in-depth — dialogs close only on explicit user intent (`LifecycleDialogs.tsx`):** Both `TerminateDialog` and `ExtendDialog` now reset their typed fields **only on the closed→open edge**, tracked via a `wasOpen` ref, instead of on every effect run while `open` is truthy. `ExtendDialog` additionally now reads `currentSeverity` from a ref (`currentSeverityRef`) rather than from the effect dependency array — previously a background re-render that swapped the alert object's `severity` prop while the dialog was open would re-run the effect and wipe the in-progress reason, severity choice, and appended note. The only close paths remain the Cancel button (`onCancel`), the native `cancel`/Esc event (`preventDefault` → `onCancel`), and a successful submit (`onSubmit`). No outside-click / blur / focus-loss close handler was added.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] ExtendDialog reset state on benign re-render via `currentSeverity` effect dependency**
- **Found during:** Task 2
- **Issue:** `ExtendDialog`'s reset effect had `[open, currentSeverity]` as its dependency array and unconditionally called `setReason('')` / `setSeverity(...)` / `setAppended('')` whenever it ran with `open` truthy. A background `alert_updated` that changed the alert's severity prop while the dialog was open would re-run the effect and wipe the user's in-progress input — the same class of bug the plan targets, on the Extend path. The plan's behavior spec ("Reason text is preserved while the dialog stays open across background renders") required this be fixed for the symmetric Extend case.
- **Fix:** Moved `currentSeverity` out of the effect deps and read it from `currentSeverityRef`; gated all resets behind the `wasOpen` closed→open edge so the effect (now `[open]` only) cannot wipe state on a benign re-render.
- **Files modified:** frontend/src/components/pipeline/LifecycleDialogs.tsx
- **Commit:** cec330d
